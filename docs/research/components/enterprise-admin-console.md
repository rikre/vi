# 企业商业化管理后台：需求拆解与方案

## 1. 基于现有功能的调研结论

当前产品已具备创作、项目、资产、技能、发布、团队、充值和会员订阅等前台能力，商业化后台需要成为这些能力的“控制面”，不能再由定价页常量或账户页模拟数据各自维护。

现有定价体系已经包含个人与团队套餐、月/季/年周期、积分包、任务并发、分辨率、水印、队列等权益；团队模块已有成员、组织、额度和账本概念；创作模块已经实际区分视频、图片和文本模型。因此后台统一抽象为：用户、订单、积分账户、消费流水、套餐、权益、模型供应和审计八类核心对象。

## 2. 产品信息架构

| 模块 | 解决的问题 | 核心能力 |
|---|---|---|
| 经营概览 | 商业化是否健康 | 注册、付费、收入、模型成本、毛利、风险预警 |
| 用户管理 | 一个用户的完整商业生命周期 | 注册与活跃时间、累计付费、累计消耗、余额分账、会员、并发、算力、白名单、风控状态 |
| 订单与消费 | 钱和算力是否可追溯 | 充值/会员/企业订单、支付渠道、退款；逐任务模型消耗、供应商成本和估算毛利 |
| 套餐权益 | 售卖什么 | 个人/团队/企业档位、价格、席位、月积分、并发、算力额度、队列、功能和模型白名单 |
| 模型 API | 供应成本与产出规格 | 供应商、端点、密钥、计费单位、成本、积分售价、路由并发、超时、图片/视频显影规格 |
| 积分与审计 | 如何扣费、谁改过配置 | 汇率、积分账户扣减顺序、有效期、失败退回、负余额策略、全量管理日志 |

## 3. 用户与企业客户模型

用户账户必须区分四个积分桶：充值积分、会员积分、赠送积分、企业积分。四者的财务属性、有效期和退款规则不同，不能只存一个 `balance`。

用户详情最少包含：

- 身份：用户 ID、手机/邮箱、昵称、头像、所属企业。
- 生命周期：注册时间、最近活跃时间、首次付费时间、最近付费时间。
- 商业价值：累计实付、累计退款、累计积分消耗、任务数、模型成本。
- 权益：会员档位与到期日、并发上限、月算力额度、席位、功能/模型白名单。
- 风控：正常、风险观察、停用；状态变更必须注明原因。

定向发放支持三种原子操作：加积分、配会员、配算力。每次操作必须记录管理员、用户、前后值、原因、时间和关联企业合同/工单号。批量发放可在第二阶段增加 CSV 导入和审批流。

## 4. 套餐与权益设计

套餐使用统一数据结构，通过 `audience` 区分个人、团队、企业，避免维护三套逻辑。建议档位：

| 受众 | 建议档位 | 定位 |
|---|---|---|
| 个人 | 轻量版、专业版、旗舰版 | 按月积分、速度、输出分辨率和并发逐级提升 |
| 团队 | 团队专业版 | 共享积分池、多人席位、审计、较高并发 |
| 企业 | 企业专业版、企业定制版 | 合同价、独享队列、API、私有模型、定向算力与 SLA |

权益采用 key-value/白名单模型，而不是散落的布尔字段。首批权益键包括模型访问、1080P/4K、无水印、优先/独享队列、API、私有模型、审计导出。运行时应由统一 entitlement 服务判断：`user override > enterprise override > subscribed plan > default`。

充值档位独立配置售价、基础积分、赠送积分、是否仅限首充和上下架。历史订单必须保存购买时的价格与权益快照，后续调整不能影响旧订单。

## 5. 模型 API 与积分计价

模型配置分为三层：

1. 供应层：供应商、模型 ID、API Endpoint、密钥引用、健康状态和超时。
2. 调度层：全局并发、企业专属并发、降级模型、重试和熔断。
3. 商品层：计费单位、供应商成本、积分售价、允许套餐、图片/视频输出规格。

API Key 不允许返回浏览器或存进 localStorage。管理页面只上传新密钥，服务端写入 KMS/Vault，前端仅接收 `secretRef` 和末四位。密钥读取接口永不返回明文。

积分售价应基于供应商成本、失败率、渠道费、目标毛利和活动补贴计算，并设置低毛利告警。任务流水保存模型配置版本和价格快照，避免改价后历史账本变化。

## 6. 权限与审计

建议 RBAC：

- `platform_admin`：所有权限和角色分配。
- `enterprise_admin`：用户、企业权益、套餐和模型配置。
- `commercial_ops`：套餐、充值档位、定向权益；不能查看/修改密钥。
- `finance`：订单、退款、对账和导出；不能调整模型。
- `support`：只读用户与流水，可提交补偿申请。
- `auditor`：只读审计日志。

高风险操作（大额积分、退款、密钥变更、负余额、停用企业）应增加二次确认、权限校验和可选双人审批。审计日志由服务端追加写入，普通管理员不可修改或删除。

## 7. 后端接口边界

建议以 `/api/admin` 建立服务端 BFF：

- `GET /dashboard`：经营指标与预警。
- `GET /users`、`GET /users/:id`：检索与用户全景。
- `POST /users/:id/grants`：积分/会员/算力定向发放，要求幂等键。
- `PATCH /users/:id/status`：风险与停用。
- `GET /orders`、`POST /orders/:id/refunds`：订单和退款。
- `GET /usage-ledger`：任务消费、成本和价格快照。
- `GET|POST|PATCH /plans`、`/recharge-tiers`：套餐与充值档位。
- `GET|POST|PATCH /models`、`POST /models/:id/secret`：模型与密钥。
- `GET|PATCH /credit-policy`：积分规则。
- `GET /audit-logs`：审计查询与导出。

所有写接口校验管理员角色、记录审计、支持幂等和乐观锁版本号。金额使用最小货币单位整数，积分使用整数，不能使用浮点数记账。

## 8. 当前实现与生产化阶段

本次已经实现完整可交互的后台控制台和本地状态层，用于确认信息架构、流程和视觉；包括定向权益、用户状态、套餐、充值、模型和积分规则的持久化与审计。它仍属于前端控制面原型。

生产接入按以下顺序推进：

1. 建立服务端 RBAC、用户全景、订单与双分录积分账本。
2. 将现有定价页和账户页改为读取统一套餐/账本 API。
3. 接入支付回调、退款与对账，保证签名校验和幂等。
4. 接入模型网关、KMS 密钥、任务价格快照和成本回传。
5. 增加大额权益审批、批量企业发放、财务导出与经营告警。
